### Question 2
I would choose responding to change over following a plan. A specific decision I could face when planning my Daily App is having already planned a feature and later realising that it no longer meets the requirements or needs of the application. I would rather change or replace that feature than continue with it simply because it was part of the original plan. Change is inevitable during development, so being able to adapt and readjust the plan would allow the application to continue meeting its needs as the project develops.





### Question 3
Problem 1 – Requirements are fixed too early: TaskBoard Pro does not allow requirement changes once the design phase begins. This could result in the final application no longer being relevant to the clients because their requirements or needs may change during the project. The team would still be following the original specification even if they knew it no longer met the client's needs. This conflicts with the Agile value of responding to change over following a plan.

Problem 2 – Feedback is received too late: TaskBoard Pro does not have any demos until the entire build phase is complete. This could set the developers back by weeks because they may develop features without confirming with the clients whether they actually meet their needs and specifications. Regular demos would allow the team to receive feedback earlier and make smaller changes before too much work has been completed. This conflicts with the Agile value of customer collaboration over contract negotiation.

Problem 3 – Testing is done too late: TaskBoard Pro only performs full QA testing after the entire application has been built. If a major problem is discovered during this late testing phase, it may require a large amount of work to fix and could delay the project deadline. Fixing problems this late could also cost the company more money because developers may have to redo work that has already been completed. Testing smaller parts throughout development would allow problems to be found and fixed earlier.

Iteration 1 – StudyFlow:
The first iteration would focus on creating the basic StudyFlow application where users can create and view their study boards. Once this small working feature is completed, it can be tested and feedback can be used before continuing development.

Iteration 2 – StudyFlow:
The second iteration would allow users to open a study board and add subject or topic headers to organise their different study areas. This feature would be developed and tested using what was learned from the first iteration before moving on to further features such as study topic cards.
